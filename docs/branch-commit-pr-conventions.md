# Branch, Commit and Pull Request Conventions — BrandOS

## Purpose

Every branch, commit and pull request in the BrandOS repository must carry a
resolvable Jira issue key. This document defines the naming rules, templates,
automated checks, and merge strategy that enforce this contract.

---

## 1. Branch Naming

### Pattern

```
{project-key-lower}-{issue-number}-{short-slug}
```

| Component | Rule | Example |
|-----------|------|---------|
| `project-key-lower` | Jira project key, lowercased | `bos` |
| `issue-number` | Numeric part of the Jira key | `22` |
| `short-slug` | 2–40 lowercase alphanumeric words separated by hyphens, derived from the issue summary | `jira-hermes-bridge` |

### Examples

| Jira Key | Summary | Branch Name |
|----------|---------|-------------|
| BOS-22 | Implement Jira-to-Hermes bridge | `bos-22-jira-hermes-bridge` |
| BOS-149 | Definition of Ready | `bos-149-definition-of-ready` |
| BOS-151 | Recovery Supervisor | `bos-151-recovery-supervisor` |
| BOS-36 | ORCH-008 – Define and enforce branch, commit and pull request conventions | `bos-36-orch-008-define-and-enforce-branch-commi` |

### Rules

1. The branch name **must** start with a valid Jira issue key in the form
   `{project}-{number}` (lowercased, hyphen-separated).
2. The slug portion is derived automatically by the bridge from the issue
   summary: lowercase, non-alphanumeric characters replaced with hyphens,
   trimmed, and capped at 40 characters.
3. Agents **must not** type branch names manually. The bridge generates them
   deterministically from the issue key and summary.
4. One branch per Jira issue. Never combine work from two issues in one branch.

### Implementation

Branch names are generated by `derive_branch_name()` in
`scripts/jira_hermes_bridge.py`. The function produces:

```python
def derive_branch_name(issue_key: str, summary: str) -> str:
    slug = re.sub(r"[^a-z0-9]+", "-", summary.lower()).strip("-")[:40]
    return f"{issue_key.lower()}-{slug}"
```

## 2. Commit Messages

### Pattern

```
{type}({ISSUE-KEY}): {short description}
```

| Field | Rule | Example |
|-------|------|---------|
| `type` | `feat`, `fix`, `docs`, `test`, `refactor`, `chore` | `feat` |
| `ISSUE-KEY` | Exact Jira key (uppercase project, dash, number) | `BOS-22` |
| `description` | Imperative mood, ≤ 72 chars | `implement secure Jira-to-Hermes task bridge` |

### Full Examples

```
feat(BOS-22): implement secure Jira-to-Hermes task bridge
fix(BOS-149): enforce Definition of Ready for AI dispatch
docs(BOS-36): add branch, commit and PR conventions
test(BOS-22): add eligibility and boundary tests for bridge
refactor(BOS-151): extract recovery actions into separate module
chore(BOS-23): configure autopilot cron schedule
```

### Rules

1. Every commit message **must** contain exactly one Jira issue key in
   parentheses after the type prefix.
2. The issue key **must** match the branch's issue key.
3. The description **must** use imperative mood ("add" not "added").
4. The total first-line length **should** not exceed 72 characters.
5. Multi-issue commits are not allowed. If work spans two issues, split into
   separate commits on separate branches.

## 3. Pull Requests

### Title

```
{ISSUE-KEY}: {short description}
```

Example: `BOS-22: implement secure Jira-to-Hermes task bridge`

### Body Template

Every pull request body **must** use the template at
`.github/PULL_REQUEST_TEMPLATE.md`. Required sections:

| Section | Content |
|---------|---------|
| **Jira Issue** | Exactly one `BOS-NNN` key (auto-linked) |
| **Summary** | 1–3 sentences of what this PR delivers |
| **Delivery Report** | Files changed, tests run, decisions made |
| **Test Evidence** | Output from test run, screenshots, or links |
| **Preview URL** | Link to staging/preview deployment (or "N/A" for non-visual changes) |
| **Checklist** | Self-review completed, tests pass, docs updated |

### Rules

1. One pull request maps to **exactly one** Jira issue.
2. The PR title **must** contain a valid Jira issue key.
3. The PR body **must** include all template sections (even if some say "N/A").
4. A PR without a valid issue key in the title **must** fail its check.
5. A PR that references two or more distinct issue keys **must** be rejected.

## 4. Automated Checks

`scripts/check_conventions.py` validates branch names, commit messages, and PR
metadata against these conventions. It can run as:

```bash
# Validate a branch name
python scripts/check_conventions.py --branch "bos-22-jira-hermes-bridge"

# Validate a commit message
python scripts/check_conventions.py --commit "feat(BOS-22): implement bridge"

# Validate PR title + body
python scripts/check_conventions.py --pr-title "BOS-22: implement bridge" \
                                     --pr-body pr_body.md

# Validate all commits on current branch vs main
python scripts/check_conventions.py --git-log main..HEAD
```

### Exit Codes

| Code | Meaning |
|------|---------|
| 0 | All checks passed |
| 1 | One or more checks failed |

### What It Checks

| Check | Target | Rule |
|-------|--------|------|
| Valid issue key present | branch, commit, PR | `BOS-\d+` pattern found |
| Exactly one issue key | PR title | Not zero, not two+ |
| Branch starts with issue key | branch | Pattern: `bos-\d+-` |
| Commit type prefix valid | commit | `feat\|fix\|docs\|test\|refactor\|chore` |
| PR body has required sections | PR body | All template sections present |
| Commit key matches branch key | git log | Each commit references the branch's key |

## 5. Merge Strategy

### Strategy: Squash Merge

All pull requests are merged via **squash merge** into `main`.

- The squash commit message follows the PR title format: `{ISSUE-KEY}: {description}`.
- This keeps `main` history linear and every commit traceable to exactly one
  Jira issue.

### Branch Cleanup

After merge, the feature branch is **deleted automatically** (GitHub setting:
"Automatically delete head branches"). This is enforced at the repository
level, not by agents.

### Rebase Policy

- Feature branches **should** be rebased onto `main` before merge if they fall
  behind by more than 5 commits.
- Force-push to feature branches is allowed (only the agent works on it).
- Force-push to `main` is **never** allowed.

## 6. Enforcement Matrix

| Gate | Where | What fails |
|------|-------|------------|
| Branch name check | `check_conventions.py --branch` | No valid issue key prefix |
| Commit check | `check_conventions.py --commit` | No issue key, wrong type prefix |
| PR title check | `check_conventions.py --pr-title` | Zero or multiple issue keys |
| PR body check | `check_conventions.py --pr-body` | Missing required sections |
| Git log check | `check_conventions.py --git-log` | Any commit without matching key |
| CI gate (future) | GitHub Actions | Will call `check_conventions.py` |
